Finding words in text: string matching and the Rabin-Karp algorithm

Faculty: Sree S Bhagya, Asst. Professor, Centre for AI

1. What is string matching?

DefinitionA string is a row of characters, like HELLO. String matching (also called pattern searching) means finding where a small string, the pattern, appears inside a bigger string, the text.

You do this every time you press Ctrl+F in a browser, search a document, or check a DNA sequence for a gene. Below, the pattern CAB is searched in the text DAACABCDBA. It starts at position 3. Positions are counted from 0.

Text on top, pattern lined up underneath at the spot where it matches.

Let’s use n for the length of the text (here 10) and m for the length of the pattern (here 3). Everything below is about finding the pattern quickly when n is large.

2. The simple way: check every position

The naive (brute-force) method slides the pattern along the text one step at a time. At each step it compares characters left to right and stops at the first mismatch. Try it. You can change the text and pattern; the rest of the page uses them too.

Letters A–I only (A=1 … I=9). The reason comes in section 4.
The problem with naive searchAt every position we may re-compare several characters. In the worst case that is about n × m comparisons. Can we reject most positions with one cheap check instead of many? The example below shows why this matters.

What “re-compare” means

When a letter doesn’t match, the naive method slides the pattern one step right and starts again from the pattern’s first letter. It forgets everything it just learned about the neighbouring letters, so the same text letters get compared again and again.

A bad case, with numbers

Text AAAAAAAAAB (n = 10) and pattern AAAAB (m = 5). The pattern keeps almost matching, so every position costs a lot.

There are n − m + 1 = 6 positions, and each costs about m = 5 comparisons. That is where “about n × m” comes from. For a text of 1,000,000 letters and a pattern of 1,000 letters, the worst case reaches about a billion comparisons.

Naive is not always slow. For text HELLO and pattern XYZ, every position fails on the first letter. It only becomes slow when the text keeps almost matching the pattern.

The cheap check: one number instead of many letters

Turn each window into a number (A=1, B=2, read as digits, as in section 4). Then compare one number instead of up to five letters:

Rabin-Karp does exactly this for every window. Only when the two numbers are equal does it compare letters, to confirm the match is real. Most windows are rejected by that single number check, which is why the average cost drops to about n + m. The next sections show how the number is built and updated quickly.

3. The big idea: compare fingerprints

Definition: hashA hash turns a string into one small number, its fingerprint. The hash value is that number. Mapping a large input to a smaller output is what hashing means.

Rabin-Karp computes the hash of the pattern once, then the hash of each text window of length m, and compares numbers instead of characters.

  • Hashes differ → the strings are definitely different. Skip the window.
  • Hashes equal → the strings might be equal. Check character by character to be sure.

Why “might”? Many different strings can share the same fingerprint. That is called a collision, and a collision that fools us is a spurious hit (a false alarm). Here is a real one. You can also watch it happen live in section 5.

Example of a spurious hit

Pattern CAB and a text window DAA. Use A=1, B=2, C=3, D=4, base 10 and modulus q = 11.

LettersAs digitsNumberNumber mod 11
PatternC A B3 1 2312312 = 28×11 + 4, so 4
WindowD A A4 1 1411411 = 37×11 + 4, so 4
Both hashes are 4. The numbers 312 and 411 are different, and CAB and DAA are clearly different strings, but taking the remainder after dividing by 11 squeezed both onto the same value. That is a collision. Because it fooled the hash check into saying “maybe a match”, it is a spurious hit.

What Rabin-Karp does next is the important part: it compares the letters. C≠D on the very first letter, so the window is rejected. The answer stays correct, and only a little extra time is lost.

Compare with a window that is not a collision: ACA = 131, and 131 mod 11 = 10. That is not 4, so the window is skipped immediately with no letter comparison.

How to reduce spurious hits: use a larger prime for q. With q = 101, CAB gives 312 mod 101 = 9 and DAA gives 411 mod 101 = 7. They no longer collide. The trade-off is that the numbers get bigger, but they still fit easily in a program’s integer type.

4. How we compute the hash

We treat letters as digits: A=1, B=2, C=3, D=4 … and read a window as a number. This uses base b = 10, which is why the demo limits letters to A–I. Real programs use a larger base such as 256.

hash(window) = (d₁·bm−1 + d₂·bm−2 + … + dₘ·b⁰) mod q
What is d?d is the digit value of a letter in the window, using A=1, B=2, C=3 … The small number underneath says which letter: d₁ is the first (leftmost) letter, d₂ the second, and dₘ the last (rightmost) letter, where m is the window length. b is the base and q is the modulus.

Each d is multiplied by a power of b. That power is its place value, just like the digits of an ordinary number: the leftmost letter gets the highest power bm−1 and the rightmost gets b⁰ = 1. Without place values, CAB and ABC would both add up to 3 + 1 + 2 = 6 and look identical. With them, CAB becomes 312 and ABC becomes 123, so the order of letters matters.

Worked out for the window CAB (m = 3, b = 10):

The mod q part keeps numbers small by taking the remainder after dividing by q. Choose q prime so values spread out well and don’t overflow on long patterns.

The rolling trick

Both the naive method and Rabin-Karp slide the window one letter at a time: the leftmost letter leaves and a new letter enters on the right. The difference is how much work it takes to decide about the new window.

NaiveRabin-Karp (rolling)
After slidingStarts a fresh comparison and re-reads the window’s letters one by one, from the first letterDoes not re-read the middle letters. Fixes the old number using only the letter that left and the letter that arrived
Work per windowUp to m comparisonsA fixed few operations, whatever m is
Remembers the previous window?NoYes, through its number

Computing each window’s number from scratch would again cost m steps per window, no better than naive. Rolling avoids that: remove the leftmost digit, shift everything left, and add the new digit on the right, all in one calculation on the old number.

new = ( b · (old − first·bm−1) + next ) mod q

For text DAAC…, window DAA = 411 rolls to AAC = 113. Compare the two ways of getting 113:

  • From scratch: read A, A, C and compute 1×100 + 1×10 + 3 = 113. That is m = 3 letters read (1000 letters if the pattern were 1000 long).
  • Rolling: 10 × (411 − 4×100) + 3 = 113. It uses the old number 411, the letter that left (4) and the letter that arrived (3). The middle letters A and A are never touched, however long the pattern is.

Step by step: take away the 4 (400), leaving 11, shift to 110, add 3. The value bm−1 (here 100) is worked out once at the start and reused for every window.

6. The steps in one place

  1. Compute the hash of the pattern.
  2. Compute the hash of the first window of the text (same length as the pattern).
  3. If the two hashes are equal, compare the characters. If they all match, report the position.
  4. Slide one step: roll the hash to the next window.
  5. Repeat steps 3–4 until the window reaches the end of the text.
def rabin_karp(text, pat, q=101, b=256):
    n, m = len(text), len(pat)
    h = pow(b, m-1, q)            # b^(m-1) mod q
    hp = ht = 0
    for i in range(m):            # hash pattern + first window
        hp = (b*hp + ord(pat[i])) % q
        ht = (b*ht + ord(text[i])) % q
    found = []
    for i in range(n - m + 1):
        if hp == ht and text[i:i+m] == pat:   # verify!
            found.append(i)
        if i < n - m:           # roll to next window
            ht = (b*(ht - ord(text[i])*h) + ord(text[i+m])) % q
    return found

print(rabin_karp("AAAABCAEAAABCBDDAAAABC", "AABC"))  # [2, 9, 18]

The code above prints matches at positions 2, 9 and 18.

7. How fast is it?

Numbers update with your text and pattern.
  • Average case: about O(n + m). One pass over the text, a few verifications.
  • Worst case: O(n × m). If almost every window collides (for example text AAAAAAAA, pattern AAB with a tiny q), you verify nearly every window.
  • Superpower: it can search for many patterns at once. Keep their hashes in a set and test each window against it.

Recap

  • String matching = find a pattern inside a text.
  • Naive checks every position character by character: slow in the worst case.
  • Rabin-Karp compares hash numbers first and only checks characters when hashes agree.
  • A rolling hash updates each window in one step.
  • Equal hashes can be a collision, so always verify before reporting a match.
